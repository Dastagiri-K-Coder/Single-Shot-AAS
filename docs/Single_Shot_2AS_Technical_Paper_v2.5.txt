====================================================================== 1.
EXECUTIVE ABSTRACT
======================================================================

Single Shot 2AS is an edge-to-cloud automated attendance management
platform designed to capture and authenticate an entire classroom cohort
from a single high-resolution classroom image. The supplied v2.0
architecture combines local authentication, role-based access control,
multiple camera ingestion modes, computer-vision recognition, Google
Drive/Sheets synchronization, three-level attendance fallback, offline
voice processing, and a Progressive Web App.

The v2.0 system is organized around eight synchronized subsystems:

1.  Local Authentication and Session Management: SQLite-backed
    authentication, bcrypt password hashing with rounds=12, UUID4
    session tokens with eight-hour expiry, account lockout after five
    failed attempts, and audit logging. Google OAuth is retained for
    Google Sheets/Drive API access rather than primary daily login.

2.  Role-Based Access Control: Admin and faculty roles. Faculty access
    is scoped to assigned sections and cameras, while administrators
    have broader system access.

3.  Multi-Mode Camera Ingestion: RTSP camera, fixed IP camera, local
    webcam, and faculty smartphone HTTP multipart upload. Smartphone
    upload is the primary v2.0 capture mode.

4.  Standards-Compliant Vision Pipeline: Quality gating, adaptive
    resolution scaling, OpenCV YuNet with dlib HOG/CNN fallbacks, IEC
    62676-4 and ISO/IEC 19794-5 resolution checks, and 128-dimensional
    metric embeddings.

5.  Google Drive/Sheets Backend: Google Drive and Google Sheets are used
    as the cloud reporting and synchronization layer. Attendance columns
    can encode subject and period, such as “9/17 DBMS P3”. Batch updates
    reduce API request volume.

6.  Three-Level Attendance Fallback: L1 manual student toggle, L2
    individual close-up retake, and L3 bulk manual addition.

7.  Voice and TTS: Offline Vosk speech recognition, debounce protection,
    and pyttsx3/espeak speech synthesis.

8.  Progressive Web App: Flask-served PWA allowing faculty to use a
    smartphone browser as the primary capture interface without APK
    distribution.

The supplied paper reports 90 unit test functions across 12 unit-test
files, plus web-route integration tests.

The proposed v2.5 architecture preserves this foundation but introduces
a persistent attendance state machine, durable local attendance records,
recognition jobs, a synchronization outbox, idempotent operations,
explicit recovery behavior, worker-based processing, structured
observability, and clear API/database boundaries.

2. SYSTEM OBJECTIVES
======================================================================

The supplied v2.0 paper defines the following major objectives:

-   Single-shot classroom attendance for approximately 35-60 students.
-   Smartphone-based high-resolution classroom capture.
-   Local computer-vision inference.
-   Offline operation of the vision and voice components.
-   Institutional multi-section and multi-camera support.
-   Standards-oriented face-quality gating.
-   Google Sheets/Drive synchronization.
-   Faculty/admin RBAC.
-   Three-level correction for missed students.
-   PWA-based faculty workflow.

The v2.5 engineering objective is:

CAPTURE -> RECOGNIZE -> VERIFY -> DURABLY COMMIT LOCALLY -> SYNCHRONIZE

rather than making cloud synchronization part of the fundamental
attendance transaction.

5. CAMERA AND CAPTURE ARCHITECTURE
======================================================================

Four documented capture modes:

A. RTSP cv2.VideoCapture(rtsp_url), including a warm-up sequence.

B. Fixed IP camera Configured through IP_CAMERA_URL.

C. Local webcam Used when network-camera sources are not selected.

D. Mobile upload Faculty smartphone sends a classroom image through HTTP

6. COMPUTER VISION PIPELINE
======================================================================

Documented v2.0 pipeline:

RAW CLASSROOM IMAGE | v 1. QUALITY GATING - minimum image dimensions -
brightness threshold - Laplacian-variance sharpness test | v 2. ADAPTIVE
SCALING - width >= 3840 px -> 0.5x - width >= 2560 px -> 0.75x - width <
2560 px -> 1.0x | v 3. FACE DETECTION - OpenCV YuNet FPN - dlib HOG
fallback - optional dlib CNN | v 4. BIOMETRIC STANDARDS GATING - native
face width >= 80 px - native face height >= 80 px - IPD >= 30 px | v 5.
EMBEDDING / MATCHING - 128-dimensional metric embedding - Euclidean face
distance - configured tolerance documented as 0.55 | v ATTENDANCE RESULT

Detection statuses include: - valid - low_resolution - low_ipd

The paper specifically documents that substandard detections are
excluded from matching.

8. GOOGLE DRIVE / SHEETS ARCHITECTURE
======================================================================

The documented Drive hierarchy uses: - application root - institution
configuration - section folders - attendance spreadsheet - classroom
audit snapshots.

Worksheet schema: - Column 1: Name - Column 2: Email - Column 3:
Gender - Column 4: PIN - Column 5+: date/subject-period attendance
columns.

Example subject-period column: “9/17 DBMS P3”

The documented batch mutation strategy: 1. Read worksheet headers. 2.
Create the target date/period column if necessary. 3. Map student names
to worksheet rows. 4. Construct the batch payload. 5. Perform one
batch_update() operation.

The paper also documents exponential backoff for selected Google API
transient errors including 429, 500, 502, 503 and 504.

======================================================================
9. THREE-LEVEL ATTENDANCE FALLBACK
======================================================================

L1 — Manual Toggle

Used for small discrepancies and missed students.

L2 — Individual Close-Up Retake

Faculty captures an individual student. The documented implementation
can temporarily restrict the recognition engine to that student’s
encodings.

L3 — Bulk Manual Addition

Faculty selects multiple enrolled students and marks them present.

Finalization in v2.0 releases the camera lock, resolves Google
credentials, writes the attendance event, and dispatches the faculty
summary.

12. v2.5 PRODUCTION ARCHITECTURE
======================================================================

The v2.5 proposal does not replace the v2.0 recognition or capture
design.

It changes the durability model.

CURRENT CONCEPT: Capture -> Recognition -> Google Sheet

PROPOSED: Capture -> Attendance Session -> Recognition Job -> Human
Verification -> Local SQLite Commit -> Durable Outbox -> Google Sync

This separates the operational attendance transaction from the cloud
synchronization transaction.

======================================================================
15. v2.5 TRANSACTION MODEL
======================================================================

Attendance finalization should use one local transaction:

BEGIN TRANSACTION

1.  Verify session ownership.
2.  Verify session state.
3.  Validate attendance records.
4.  Persist final session state.
5.  Persist student attendance records.
6.  Create synchronization outbox event.
7.  Mark session LOCAL_COMMITTED.

COMMIT

If any operation fails: ROLLBACK.

Only after local commit succeeds should the user be told that attendance
has been saved.

Google synchronization is then performed independently.

======================================================================
16. v2.5 IDEMPOTENCY
======================================================================

Every synchronization event receives: - event_id - idempotency_key

The idempotency key must uniquely identify the logical attendance
operation.

A repeated finalize request with the same key must return the existing
result rather than create a duplicate event.

This protects against: - browser retries, - network retries, - double
taps, - process recovery, - synchronization retries.

======================================================================
17. v2.5 SYNCHRONIZATION WORKER
======================================================================

OUTBOX | v PENDING | v PROCESSING | +—- SUCCESS —-> SYNCHRONIZED | +—-
FAILURE —-> RETRY_WAIT | v PROCESSING

After a defined retry limit: PERMANENT_FAILURE

The existing exponential-backoff mechanism should be retained and
integrated with this durable state.

======================================================================
18. v2.5 WORKER ARCHITECTURE
======================================================================

HTTP requests should not be responsible for unlimited CPU-heavy
recognition or long-running synchronization.

Proposed logical workers:

1.  WEB WORKER Handles HTTP requests and lightweight validation.

2.  CV WORKER Processes recognition jobs.

3.  SYNC WORKER Processes durable Google synchronization events.

4.  OPTIONAL NOTIFICATION WORKER Handles email/TTS tasks that do not
    need to block the attendance commit.

Logical topology:

Faculty Phone | v HTTP/Web Layer | v Attendance Session | v CV Job Queue
| v Recognition Worker | v Human Review | v SQLite | v Sync Outbox | v
Sync Worker | v Google APIs

This worker separation is a proposed v2.5 design.

======================================================================
19. v2.5 UPLOAD SECURITY BOUNDARY
======================================================================

The proposed upload pipeline is:

Authentication | Camera authorization | Content-Type validation |
Maximum request-size validation | Temporary file | Actual image decode |
Dimension validation | Quality validation | Atomic rename | Attendance
session

Filename extension and client-supplied Content-Type must not be treated
as proof that a file is a valid image.

23. v2.5 RECOVERY ARCHITECTURE
======================================================================

Failure: phone disconnects

Preserve the persistent session. Do not lose already uploaded data.

Failure: malformed image

Reject before recognition and record the failure.

Failure: recognition crash

Mark the recognition job failed/interrupted and permit retry.

Failure: browser refresh

Reload the persistent attendance session by session_id.

Failure: Google API unavailable

Keep the attendance locally committed and leave the outbox event
pending.

Failure: internet disappears

Continue local operation. Synchronize when connectivity returns.

Failure: power loss after local commit

Recover the pending outbox event during startup.

Failure: duplicate finalize

Use the idempotency key and return the existing operation result.

Failure: camera unavailable

Release/recover the camera resource and preserve the attendance session
where possible.

33. ARCHITECTURAL PRINCIPLES
======================================================================

1.  Local attendance must not depend on WAN availability.

2.  Recognition and attendance decision are separate concepts.

3.  Human correction is a first-class workflow, not an exception hidden
    inside the recognition engine.

4.  SQLite is the proposed operational source of truth for v2.5
    attendance.

5.  Google Sheets/Drive remains the cloud reporting/synchronization
    destination.

6.  Synchronization must be durable and retryable.

7.  Repeated requests must be idempotent.

8.  Every attendance session must have a persistent identity.

9.  Every manual correction must have provenance.

10. Recognition configuration should be traceable.

11. HTTP handlers should remain thin; business logic belongs in
    services.

12. Failure recovery must be designed explicitly rather than inferred
    from exception handling.

34. ENGINEERING SUMMARY
======================================================================

Single Shot 2AS v2.0 provides the foundational architecture for a
faculty-handset-based automated attendance system. Its core strengths
are the combination of local authentication, multi-mode capture, edge
recognition, standards-oriented image-quality gating, subject-period
attendance columns, three-level correction, RBAC, offline voice
processing, and PWA delivery.

The production-hardening work represented by v2.5 does not require
replacing those concepts.

The central evolution is the introduction of durable state:

CAPTURE -> RECOGNITION -> HUMAN VERIFICATION -> LOCAL COMMIT -> DURABLE
OUTBOX -> CLOUD SYNCHRONIZATION

This transforms the cloud synchronization layer from a critical part of
the attendance transaction into a recoverable downstream process.

The resulting architecture can therefore tolerate, subject to
implementation and validation: - temporary internet failure, - browser
refresh, - duplicate requests, - recognition-job interruption, -
synchronization failure, - process restart, - and power loss after a
successful local transaction.

These v2.5 capabilities are engineering proposals derived from the
existing v2.0 architecture and should be validated through
implementation, integration testing, and real deployment measurements
before being described as completed system properties in a publication.

35. CLAIMS REQUIRING EMPIRICAL VALIDATION
======================================================================

Before publication, the following claims should be backed by measured
experiments rather than architecture alone:

-   end-to-end attendance latency,
-   classroom-size recognition throughput,
-   recognition precision/recall,
-   false acceptance and false rejection rates,
-   rear-row recognition performance,
-   Raspberry Pi versus x86 processing time,
-   memory consumption,
-   Google synchronization latency,
-   behavior under sustained classroom load,
-   actual operational cost,
-   network-outage recovery,
-   biometric-data retention behavior,
-   and production security testing.

The supplied paper reports a “<3 sec” throughput figure, “$0” recurring
cost, and “100% offline” operation in its comparative analysis. Those
values are documented source claims, but production publication should
distinguish architectural capability from experimentally measured
deployment results.

38. FINAL ARCHITECTURAL STATEMENT
======================================================================

Single Shot 2AS is structured around an edge-first attendance workflow
in which classroom capture and biometric processing remain local while
Google Drive/Sheets provides the existing cloud reporting and
synchronization layer.

The v2.5 production architecture preserves the documented v2.0
mechanisms while introducing a durable transaction boundary:

ATTENDANCE EXISTS LOCALLY FIRST. CLOUD SYNCHRONIZATION HAPPENS
AFTERWARD.

The proposed system boundary is therefore:

Faculty Phone -> Secure API -> Persistent Attendance Session ->
Recognition Worker -> Human Verification -> SQLite Local Commit ->
Durable Sync Outbox -> Google Sheets/Drive

This specification provides the logical foundation for implementing the
next production-hardening phase without discarding the existing Single
Shot 2AS v2.0 architecture.
